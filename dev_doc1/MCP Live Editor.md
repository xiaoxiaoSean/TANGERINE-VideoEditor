# MCP 实时编辑器接管

本功能让 MCP 客户端操作已经打开的软件窗口。项目、播放头、选择和后台任务属于目标窗口的实际状态。多个软件进程可以同时运行，AI 必须选择它要操作的进程。

## 配置与启动

1. 构建并打开新的 TANGERINE-VideoEditor。较早启动的软件进程不包含新加入的 MCP 接口。
2. 从软件菜单打开「帮助 → AI / MCP 连接」，读取当前进程 ID、连接状态和适用于当前安装位置的客户端配置。
3. 把窗口中显示的配置加入所使用的 MCP 客户端。桥接程序使用标准输入输出；不要给它配置 HTTP 地址或端口。
4. 客户端连接后调用 `list_instances`，确认项目名称、项目路径、进程 ID 和启动时间，然后用 `select_instance` 选择目标。
5. 调用 `editor_control_acquire` 进入目标进程的 MCP 控制模式，成功后才能执行应用命令。完成操作后调用 `editor_control_release` 退出控制模式。

配置结构如下，`command` 使用连接窗口里实际显示的绝对路径：

```json
{
  "mcpServers": {
    "tangerine-video-editor": {
      "command": "C:\\实际安装目录\\mcp\\TANGERINE-VideoEditor.Mcp.exe",
      "args": []
    }
  }
}
```

桥接服务本身也可以通过 `dotnet TANGERINE-VideoEditor.Mcp.dll` 启动，适用于只部署 DLL 的开发环境。它使用官方 MCP SDK，标准输出专供协议 JSON-RPC，日志通过标准错误输出。具体通信与身份检查见 [MCP Transport.md](MCP%20Transport.md)。

## 多进程工作流

`select_instance` 的选择只影响当前 MCP 会话，不切换用户桌面的前台窗口，也不启动或关闭其他编辑器。每个编辑工具还接受可选 `processId`，可以在同一会话中轮流操作多个项目。

进程选择示例：

```json
{ "processId": 12345 }
```

这是 `select_instance` 的输入。实际 PID 从 `list_instances` 返回值取得。多个窗口存在时，省略进程选择会得到明确错误。选定进程退出后，命令不会自动落入其他窗口；PID 被重用时还会检查随机实例身份。

## MCP 控制模式

AI 必须先取得目标进程的控制模式，再读取或操作它的项目与界面。`editor_control_acquire` 没有必填参数，可用 `ownerLabel` 标记当前任务；同一个应用进程同时只接受一个 MCP 会话的控制。除申请、释放、查询控制模式外，所有编辑器命令都要求同一会话持有控制权，包括只读状态、模型 schema 和等待变化。工具列表、实例发现和进程选择仍然可以在获取之前使用。`editor_control_status` 可以在未持有控制权时查询当前状态，而且不会刷新空闲计时。`ownerLabel` 仅用于显示，真正的会话身份由 MCP 桥接服务自动附带，AI 不能通过修改名称获得其他会话的权限。

申请控制权示例：

```json
{ "ownerLabel": "整理字幕与转场" }
```

完成编辑、保存或导出后，调用不带业务参数的 `editor_control_release`。释放只作用于当前会话持有的控制权。如果命令或后台任务仍在执行，释放返回 `MCPCT0004` 忙碌错误；先等任务完成，或者调用 `jobs_cancel` 并确认任务结束，再重新释放。不同进程的控制模式彼此独立；`select_instance` 仅切换路由，不会替 AI 自动获取新进程或释放旧进程。

忘记释放时，软件在连续空闲 60 秒后自动退出控制模式。一分钟是固定的空闲时长，不是单个任务的最长执行时间。正在执行的操作、等待变化和仍在运行的后台任务暂停空闲计时，长导出或长分析会继续执行；命令或任务结束后重新计算完整的 60 秒。当前拥有者重复调用 `editor_control_acquire` 会刷新空闲时间，查询 `editor_control_status` 则不会。应等必要任务完成或取消，再主动释放，不依靠超时完成正常的工作流程。

## 实时刷新约定

接管期间用户仍可通过轨道区的纵向滚轮、横向滚轮及 Shift＋滚轮浏览视图，不能编辑项目或用 Ctrl＋滚轮缩放。视图滚动不会更新项目版本或续期 MCP 空闲计时；其他区域滚轮与编辑输入仍受拦截。轨道导航和原生横向滚轮实现见 [Track Navigation and Naming.md](Track%20Navigation%20and%20Naming.md)。

每个编辑命令在目标窗口的 WPF Dispatcher 上执行。片段增删移动、轨道修改、文字样式、转场、关键帧、音频设置、素材和序列操作都更新同一份内存模型，并进入现有撤销历史。成功提交后同步重建相关时间线、素材库和属性内容，失效旧的合成缓存，再请求实际预览。

编辑响应在 WPF 处理刷新后返回。需要 FFmpeg 合成的画面可能仍在异步生成，因此「已提交」与「新画面已生成」是两种不同状态；客户端可以读取 `editor_get_state.preview.rendering`、`pending`、`failed` 和 `generation`，准确判断预览是否完成。静态模型编辑失败会回滚，不会留下部分改动。

状态包含两个版本：

| 字段 | 用途 |
| --- | --- |
| `revision` | 项目编辑版本。写操作的 `expectedRevision` 与此字段比较，防止覆盖过期项目状态。 |
| `uiRevision` | 界面状态版本。播放头、选择、播放状态等界面变化也会推动此版本，用于观察实时变化。 |

获取控制模式后，首次调用 `editor_get_state` 获取项目、稳定对象 ID 和版本。只需要轻量状态时传入 `includeProject: false`。随后用 `editor_wait_for_change` 等待 UI 变化，再按需获取完整模型：

```json
{ "afterUiRevision": 20, "timeoutMilliseconds": 30000 }
```

等待不会冻结软件界面；鼠标编辑、AI 修改或播放状态变化都应能唤醒等待。返回后使用最新 `uiRevision` 作为下一次等待游标。`timeoutMilliseconds` 最大 30 秒，超时属于正常结果，不代表软件出错。

## 编辑与后台任务

推荐的编辑流程是「选择进程 → 获取 MCP 控制模式 → 读取状态 → 查询 schema 或预设目录 → 使用对象 ID 编辑 → 检查响应与预览 → 完成或取消必要后台任务 → 释放控制模式」。文字、转场和效果参数从 `model_get_schema`、`catalog_schema` 查询，避免凭猜测使用名字或参数。所有结构化工具及字段见 [MCP Commands.md](MCP%20Commands.md)。

并发写入示例：

```json
{
  "clipId": "当前状态中的片段ID",
  "patch": { "opacity": 0.8 },
  "expectedRevision": 12
}
```

把以上参数交给 `clip_update`。如果用户已在软件里把项目修改到版本 13，此请求会返回 `revision_conflict`。客户端应读取新状态并重新决定修改，不要盲目删除版本保护重试。

视频导出、图片捕获、示例渲染、代理、波形、响度、场景切点、重构图、遮罩跟踪和语音识别使用后台任务。启动命令立即返回 `jobId`，通过 `jobs_status` 读取进度与输出，通过 `jobs_cancel` 取消。取消只终止该任务拥有的外部处理进程。录音采用单独的开始、停止保存和取消命令。

## 错误与验证

错误响应包含 `success: false`、错误代码、中文说明和 `stageCode`。典型错误包括：实例已退出、未选择多个实例中的目标、版本冲突、轨道锁定、文件不存在、参数类型或范围错误、项目读写中、任务被取消。应用或传输错误不会伪装成成功结果。

新建、打开和关闭项目会检查未保存修改。AI 需要先保存，或者显式提供 `discardChanges: true`。删除轨道或片段是可撤销的项目编辑；从项目移除素材不会删除原媒体文件。

验证分为共享协议检查和真实软件检查。共享检查覆盖官方 MCP 握手、两个真实子进程的发现和路由、取消、实例退出、JSON 参数与原子补丁。真实软件检查应覆盖编辑后的时间线和属性内容、撤销、预览变化、多个进程间隔离以及实际导出文件。仅通过协议检查不能证明 WPF 界面已经刷新。

本次命令行回归结果：通信与官方客户端互操作 113 项、实际窗口与界面刷新 83 项、控制模式与真实输入事件 43 项、高级编辑和真实媒体输出 81 项全部通过。发布构建已验证包含独立 MCP 程序及其运行依赖。60 秒空闲回收测试通过推进最后活动时间验证，同时覆盖正在执行命令、后台任务及任务收尾回调时保持锁定；不会为了等待超时而终止任务。
